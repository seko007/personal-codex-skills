# 仕様駆動開発の小さな運用

期待結果の判断を人が行い、AIが調査・下書き・計画・実装・検証を支援するための任意の運用です。既存の開発方式と承認手順がある場合は、それに合わせて採用してください。

## 文書の役割

現在仕様、今回の変更、過去の履歴を区別します。配置例は `docs/spec/`、`docs/changes/`、`docs/archive/` ですが、利用先の階層に合わせられます。

- 現在仕様: 現在有効な業務ルールと期待挙動。
- 変更仕様: 今回の差分、対象外、受入条件、未決事項。
- 計画・作業: 実現方式と検証結果。現在仕様の代替にはしない。
- 履歴: 完了した変更の理由・確認結果。必要なときだけ読む。

## 進め方

| 時点 | AIの作業 | 人の判断 |
| --- | --- | --- |
| 変更仕様 | 現在仕様・コード・テスト・契約を確認し、変更仕様だけを下書き | 期待結果、対象外、例外、未決事項 |
| 計画 | 確認済みの仕様から計画と作業一覧を作成 | 方式、影響、検証方法、実装開始 |
| 実装・検証 | 許可範囲を実装し、確認結果と未確認を記録 | 結果、残課題、正本への反映内容 |
| 完了 | 確認済み内容を現在仕様・契約・手順へ反映し、変更記録を履歴へ | 反映内容と完了 |

仕様確認前に計画・作業一覧・実装・テストを作成しない方式を採用する場合は、その開始条件を利用先の指示書に明記します。既に確認・許可された内容を再承認させる運用にはしません。

受入条件、認可、状態遷移、削除、外部送信が未決なら、実装やテストの期待値を推測しません。判断に依存しない調査と、選択肢の比較は進められます。

軽微で仕様を変えない修正は、チケットやPRの説明と確認結果で十分な場合があります。変更ごとに同じ数の文書を必須にせず、利用先の基準で判断します。
