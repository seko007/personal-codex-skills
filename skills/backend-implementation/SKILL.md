# Backend Implementation

## 開始前

利用先の `AGENTS.md`、該当する実装規約、現在仕様・受入条件、APIやデータ契約、関連コード・テストを確認する。技術やバージョンはマニフェストとロックファイルを根拠にする。

作業範囲、関係する層、検証方法を簡潔に説明する。既に得ている開始許可を尊重し、プロジェクトに承認段階がある場合はそれに従う。受入条件、権限境界、状態遷移、削除、外部送信の意味が未決なら、その判断に依存する実装・テスト期待値を作らない。

## 実装

1. 関連する仕様を入力・検索・保存・返却・副作用の観点で確認し、対象外と未確認を分ける。項目追加では検索と一覧返却を別々に確認する。
2. [整合性と実装境界](references/implementation-safety.md) を読み、既存アーキテクチャへ適用する。特定のORM、層構成、DTOの引数数を強制しない。
3. DB変更・既存データ変換を伴うときは [移行の安全確認](references/database-migration-safety.md) を読む。
4. 「既存と同様」は実際の入力型、null・空値、保存値、返却形、CSV、履歴、認可で比較する。互換処理は実在する既存データ・利用者・反映済み環境に基づいて設計する。
5. 大きい変更は、利用者が挙動を確認できる単位へ分ける。承認が既にある範囲内は継続し、仕様や権限が変わる場合は判断を求める。
6. 状態、冪等性、競合、非同期処理を扱う場合は、成功・失敗・復旧と切替条件を実装前に明文化する。`pre-implementation-matrix` が利用可能なら使い、なければ同じ観点を直接整理する。
7. プロジェクト指定の環境で必要なテスト・確認を行う。DB制約やロックなどは実DBに対する確認を含める。テストの担当範囲は依頼と規約に従う。

## 完了

変更差分を確認し、無関係な整形やリファクタリングを混ぜない。既存スタイル差分を理由にファイル全体を整形しない。

仕様への対応、変更による挙動、検証結果、未確認・対象外、既存環境への反映方法を報告する。ユーザーがコード説明を求めた場合は、変更した処理の役割と前後の違いも説明する。移行・照合・復旧などの重要な確認が残る場合は完了と扱わない。
