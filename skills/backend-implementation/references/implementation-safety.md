# 整合性と実装境界

## 境界

- HTTP、CLI、ジョブなどの入口で入力を検証・正規化し、業務処理へ明確な型と意味を渡す。既存の責務分担に合わせ、入口固有の依存を不必要に業務処理へ持ち込まない。
- 時刻、認証主体、外部APIなどを検証時に差し替えられる構造を検討する。今回の変更に必要な範囲で行う。
- 定数の置き場は既存規約に従う。業務値と技術上の局所値を区別し、共有する意味がある値だけを共通化する。
- エラーは利用者が入力を直せるものとシステム障害を区別する。内部キーや例外詳細を利用者へそのまま返さない。

## APIと保存値

- 項目を追加するときは、候補一覧、検証、型変換、プレビュー、本実行、保存、検索、レスポンス、CSVまで関連経路を辿る。
- 未指定・null・空文字・ゼロ・falseを同一視しない。入力の正規化とDB制約・出力契約を合わせる。nullと一意制約の動作は利用するDBで確認する。
- JSONや検索条件は境界で型を確定させ、業務処理の各層で繰り返しデコードしない。保存・返却の境界を明確にする。

## データ整合性

- 重複禁止はDB制約で守れるかを先に検討する。アプリケーションの事前チェックだけでは競合を防げない。
- 状態条件がある更新は条件付き更新や比較更新を検討する。複数書き込みの整合性にはトランザクションを使い、必要に応じて行ロックまたは楽観的競合検知を選ぶ。
- DBトランザクションと外部送信の成功を同一視しない。コミット前後の失敗、重複送信、再実行方法を決める。必要なら送信台帳やoutboxなどを検討し、常に追加するわけではない。
- 実行結果が不明になった場合にも、操作IDなどで結果照合できるか確認する。

## 大量処理

- 最大対象件数、応答時間、メモリ、ロック時間を見積もる。全IDのメモリ展開や1件ずつのDB往復を当然の前提にしない。
- 分割する場合は安定した一意キーと対象変化を考慮する。更新対象の値でページングすると取りこぼしが起きる場合がある。
- 一括更新、分割処理、ジョブ化を件数と失敗時の要件から選ぶ。分割コミットが許容されるかを確認してから採用する。
- サンプル・プレビューと本処理で対象条件を一致させる。予測件数と実処理件数を照合できるようにする。
- 性能対応は代表データで変更前後を測定する。計測や実行計画なしにインデックスヒントや処理方式を固定しない。
