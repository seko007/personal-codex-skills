# Code Review

レビュー対象に起因する問題を、発生条件と影響が分かる形で示す。レビュー依頼は、コード変更やマージ、外部コメント投稿の許可にはしない。

## 調査

1. 指定された比較元・比較先・コミット・作業ツリーを確認する。指定がない場合は既存のレビュー文脈から候補を絞り、結果を左右する曖昧さだけを確認する。既存の未コミット変更を保持する。
2. 差分の規模と対象ファイルを確認してから、ファイル・処理単位で読む。巨大な差分、文書、ログを一括で取得しない。
3. 利用先の規約、現在仕様、受入条件、契約を差分と照合する。仕様が不足していても確認可能な実装レビューは進め、仕様適合の判断は未確認として分ける。
4. 入力、認可、正規化、検索、保存、レスポンス、非同期処理・外部送信まで追跡する。共有入力や同じ業務概念を使う関連経路も確認する。
5. API・項目・検索・集計・CSV・マスタの変更では [契約の横断確認](references/contract-review.md) を読む。
6. 状態、再実行、並行処理、移行、外部副作用を変更する場合は [復旧と整合性](references/recovery-review.md) を読む。
7. 変更のリスクに応じて関連テストと実行結果を確認する。テスト数や命名だけで評価せず、外から観測できる契約を検証できるか判断する。未実行のテストを成功と書かない。

## 指摘

重要な指摘を先に置き、次を含める。

- 重大度と短い題名
- 問題の場所（ファイル・行・設定・クエリなど）
- 発生条件と影響
- 問題を裏付けるコード・仕様・確認結果
- 修正または追加確認の方向

確認済みの不具合、仕様の未決事項、任意の改善を区別する。変更前から存在する問題は、今回悪化する場合や明示された監査対象の場合に限り主指摘とする。実害のない書式の好みを不具合として指摘しない。

最後に検証範囲、未確認事項、マージ前に必要な対応を簡潔に示す。指摘がなければその旨と確認限界を示す。数値スコアは、利用先の基準または明示依頼がある場合だけ使い、重大な未解決事項を平均点で隠さない。

出力形式はユーザーの指定とプロジェクト規約に合わせる。報告書が必要な場合は配置規約に従い、その他はチャットで返す。レビュー中に関連経路の変更が必要と分かっても、指摘として提示する。
