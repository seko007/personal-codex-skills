# 復旧と整合性のレビュー

新しい永続状態や実行方式を導入した場合は、差分だけでなく状態の生成から完了・復旧まで追う。

| 確認項目 | 観測する根拠 |
| --- | --- |
| 再実行 | 初回と同一再送のレスポンス・保存値・副作用回数。異なる入力の再送の扱い |
| 競合 | 検証後の変更、一意制約、条件付き更新、ロック、コミット結果が不明な場合 |
| 可視性 | 論理削除、所属スコープ、取消、関連取得条件、並び順、再送時の完全なID集合 |
| 状態 | 許可・禁止遷移、実行主体、タイムアウト、復旧主体、監査記録 |
| 外部副作用 | DBコミットとの順序、再送・重複・失敗後の復旧、ジョブ設定 |
| 既存データ | 対象抽出、除外、移行前後の件数、残件照合、切替ガード |

入力不備、業務競合、参照先変更、一時的な障害、並行処理、コミット後送信失敗を、同じ「再試行」で片付けない。同一操作を再実行できるか、新しい操作が必要か、誰が何を直すか、利用者への案内が一致しているかを確認する。

フレームワークのスコープ、関係、コールバック、キュー設定は具体的な定義へ辿る。モックの成功だけでは、DB制約・ロック・実行環境の保証とみなさない。

移行スクリプトやテンプレートがあるだけでは完了としない。対象全体の照合と、適用前に新処理が走る場合の挙動を確認する。未確認の重要条件はマージ・リリース判断の制約として明示する。
