# 正本とライフサイクル

利用先の規則があればそれを優先する。以下は未整備のプロジェクトへ提案できる小さな管理方式である。

| 役割 | 内容・扱い |
| --- | --- |
| 現在仕様 | 承認済みの期待挙動、受入条件、業務ルール。次の変更の出発点 |
| 契約・判断 | API、データ、外部連携の約束と採用理由 |
| 変更仕様 | 今回何を変えるか、対象外、例外、未決事項 |
| 計画・作業 | 実現方式、実装順序、確認方法、実施結果 |
| 手順 | 環境構築、適用、監視、復旧などの再現可能な操作 |
| 履歴 | 完了・廃止した変更と当時の判断。現在仕様の代替にはしない |

置き場は既存構成に合わせる。未整備なら、文書の入口と「現在仕様 / 進行中の変更 / 履歴」の区別から始める。技術契約や手順の数が増えたら必要な領域を足す。

frontmatterを使う場合は、題名、文書種別、承認状態、根拠、責任者など必要な項目だけにする。YAMLの項目数を増やすことを目的にしない。履歴参照を許すか、更新停止領域を設けるかは利用先の方針で決める。

仕様駆動開発を採用する場合は、変更仕様の確認後に計画・作業へ進み、実装結果の確認後に現在仕様へ反映する。計画を現在仕様に昇格させない。

重要な認可、状態遷移、削除、外部送信などは、受入条件から実装・テスト・検証結果へ辿れるようにする。すべての行へ機械的にIDを付ける必要はない。
