# Software Effort Estimation

## 前提

課題の題名だけで見積もらず、対象ブランチ、現在の挙動、関係するコード・契約・テストを確認する。AIの利用、担当範囲、1人日の時間、表示単位は依頼やチームの慣習に合わせ、未指定の前提は短く明示する。

実作業時間と、レビュー待ち・環境待ち・承認待ちなどの経過時間を分ける。固定の実装対検証比率や、全案件共通の最小人日を強制しない。

## 見積もり

1. 確定要件、提案、未知の条件を分ける。仕様整理だけの依頼に実装や移行設計を混ぜない。
2. 範囲、データ保持、認可、共有状態、確認経路が大きく変わる選択肢だけをパターン化する。
3. 各案に含むもの・含まないもの・追加影響を示す。要件を満たさない安価な案は、その旨を明記する。
4. 類似作業の実績がある場合は先に使い、対象・データ・確認範囲の差を説明する。AIによる短縮は、確認できる実績や利用前提に基づいて扱う。
5. 次の工程から必要なものを積み上げ、幅と不確実性の理由を示す。

| 工程 | 数える作業 |
| --- | --- |
| 仕様整理・判断 | 未決事項、影響調査、選択肢比較、合意に必要な整理 |
| 検証設計・データ準備 | 再現条件、認可・状態・件数、計測データ |
| 実装・自動テスト | アプリ、移行処理、テスト、開発環境での確認 |
| 結合・回帰確認 | UI/API、複数経路・権限、CSV、バッチ、外部副作用 |
| 検証環境・レビュー対応 | 実データ相当での確認、リリース前検査、修正 |

性能対応では、基準測定、代表データ準備、ボトルネック調査、変更前後の比較を実装修正と別に数える。短い修正でも確認面が多い場合は、その理由を具体的に示す。

## 出力

背景、採用前提、工程別または案別の概算、未決事項を簡潔に示す。時間または人日を依頼に合わせて使い、各行と合計の単位を統一する。丸める場合は集計方法を示す。作業待ちは別のリードタイムとして示す。

仕様が未確定なら「現時点では仕様パターン別の概算です。採用する案と対象範囲が決まった後に再見積もりします」など、硬すぎない表現で説明する。過去見積もりとの差は、実際に増減した作業で説明する。見積もり依頼からチケットへの投稿や実装を開始しない。
