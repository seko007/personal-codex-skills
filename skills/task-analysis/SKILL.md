# Task Analysis

## 調査

1. 依頼の目的、現在の作業段階、対象・対象外、受入条件、利用する正本を整理する。調査依頼から実装開始を推測しない。
2. 利用先の規約、現在仕様、対象のコード・テスト・契約を確認する。古い計画や議論は、判断に必要な場合だけ読む。
3. 調べる観点を短く伝え、現在の挙動、変更後の期待挙動、影響を受ける経路を追う。
4. 曖昧さがある場合は、判断不要の調査を進めながら、選択肢と影響を整理する。仮説は仕様確定として扱わない。
5. 段階実装、関連APIとの責務分担、ファイル台帳を含む調査では [段階実装と責務](references/incremental-features.md) を読む。
6. 状態、冪等性、競合、移行、外部送信を含む場合は [重要な確認条件](references/risk-gates.md) を読む。`pre-implementation-matrix` が利用可能なら対応表作成に使い、別スキルがなくても調査を継続できるようにする。

## 出力

背景と結論・提案を先に示し、必要な範囲で次を整理する。

- 確定要件、提案、未決事項と根拠
- 現在の挙動と変更後の違い
- 入力・認可・検索・保存・返却・バッチ・CSV・外部連携への影響
- 実装する場合の範囲、前提、検証方法

判断事項は「現状 / 選択肢 / 影響 / おすすめ / 決めたいこと」を示す。「確認が必要」「修正が必要」だけで終わらず、具体的な処理と挙動差へ落とす。「既存と同様」は入力、型変換、保存、返却、検索、更新・空値、副作用を実例で比較する。

文書化は依頼または利用先の規約に従い、固定のローカルパスや課題番号から自動的に作業記録を増やさない。仕様駆動開発で仕様確認が先の場合は、変更仕様を下書きする段階で計画・作業一覧・実装・テストを先回りしない。

調査だけで完了できる依頼は、結果を返す。実装まで依頼された場合は、未決の重要条件を解決し、プロジェクトの開始条件と既に得た許可に沿って進める。
